## Phase 1 — Foundation

Goal: a user can sign up, create or join a company, and land on an empty but permission-gated dashboard. Nothing else is buildable without this.

- [x] **Scaffolding**: Django + DRF project (`backend/`), Next.js project (`frontend/`), Docker Compose (`postgres`, `backend`, `frontend`). - [x] **Users**: custom `User` model (email as `USERNAME_FIELD`), signup/login/logout/`me` endpoints, session auth + CSRF
  - [ ] Password reset — not built yet
- [x] **Companies**: `Company` model, self-serve create-company flow (creator becomes Owner automatically)
  - [ ] Join-an-existing-company flow (invite-by-link) — deferred; this is really Phase 2 team-invite scope per the architecture doc, not a Phase 1 blocker
- [x] **CompanyMemberships**: join table, "active company" session context (`request.company`, set by `CurrentCompanyMiddleware`), company switcher UI (frontend dashboard)
- [x] **Roles & Permissions**: `Role`, `Permission`, `RolePermission`, `MembershipRole` models; `apps/roles/seed.py` seeds the five default roles with their permissions on every company creation

- [x] **Dashboard shell**: Next.js login/signup/dashboard; dashboard renders module tiles gated by the active membership's flattened permission list — verified in a real browser that an Owner sees all five tiles enabled and a Sales Manager sees only Sales & CRM

## Phase 2 — Business Core

Backend APIs done for all seven areas, reusing the Phase 1 pattern end to end (`apps/common/rls.py`'s `tenant_policy_sql()`, `apps/common/views.py`'s `CompanyScopedViewSet`/`CompanyScopedReadOnlyViewSet`, `apps/common/serializers.py`'s `CompanyScopedSerializer`) — no module reinvented tenancy or permission checks. Verified via curl: nested line items, computed totals, stock movements updating materialized stock, cross-module permission gating, RLS + same-company FK validation on a real two-company user.

**Frontend**: all seven modules have working screens now.
- `dashboard/hr` — departments, employees
- `dashboard/inventory` — items, warehouses, live stock levels (read-only), stock movements
- `dashboard/procurement` — suppliers, purchase orders (with line items, computed totals)
- `dashboard/sales` — customers, quotations, sales orders, invoices (all with line items where relevant; invoicing from a sales order snapshots its total)

`components/LineItemsEditor.tsx` is shared by purchase orders, quotations, and sales orders — the "pick an item, quantity, price, add/remove line" interaction is identical across all three, differing only in which field name the price maps to server-side. Verified in a real browser end to end: every create flow, computed totals matching hand-checked math, the invoice-from-sales-order snapshot picking up the *correct* order's total (caught and fixed a wrong assumption in the test script itself — the order list is newest-first, so "last dropdown option" was the wrong element to pick), and a role without a module's view permission (HR Manager hitting Sales or Procurement directly by URL) getting a clean permission error with empty tables, not a crash or a data leak.

Building HR/Inventory surfaced a real backend bug, now fixed: a `UniqueConstraint` on `(company, ...)` can't be validated by DRF's automatic uniqueness check, because `company` is deliberately not a client-writable serializer field — a duplicate name was crashing as a raw 500 instead of a clean 400. `CompanyScopedMixin.perform_create`/`perform_update` now catch `IntegrityError` and turn it into a normal validation error, for every Phase 2+ module at once.

**Known gaps**: no edit/delete UI anywhere yet (list + create only, matching the API's scope choices so far); the permission-denied message on Sales/Procurement is technically accurate but generic (it surfaces whichever endpoint's 403 happened to reject first in the page's `Promise.all`, not a purpose-written "you don't have access to this module" message).

## Phase 3 — Finance

All of Phase 3 is done and verified end-to-end — including the hardest part, that a Balance Sheet generated from real transactions actually balances.

- [x] Chart of Accounts (`apps/accounting.Account`) — seeded default set per company (`apps/accounting/seed.py`, hooked into company creation the same way default roles are) via `Account.role` marking the "well-known" accounts (Cash, Accounts Receivable, Accounts Payable, Sales Revenue, Tax Payable, Default Expense) the posting engine looks up by meaning, not by name
- [x] Journal Entries / General Ledger posting engine (`apps/accounting.JournalEntry`/`JournalLine`) — append-only (`http_method_names` excludes PATCH/DELETE, same pattern as StockMovement: correcting a mistake means a reversing entry, not editing history); balanced-debits-equal-credits enforced in the serializer for manual entries, and structurally guaranteed for auto-posted ones since `posting.py` always writes matched pairs; a DB `CheckConstraint` also blocks a line from being both a debit and a credit at once
- [x] Accounts Payable / Accounts Receivable — genuinely "thin ledgers over the same journal-line mechanism" as the architecture doc says, not separate balance tables: issuing an `Invoice` (`apps.sales`) or a new `Bill` (`apps.procurement`, the AP counterpart to Invoice) auto-posts Dr AR/Cr Revenue or Dr Expense/Cr AP; recording a `Payment` (`apps.accounting`) auto-posts the clearing entry and flips the Invoice/Bill to `paid` once fully covered. Wired via Django signals in `apps/accounting/signals.py` — `apps.sales`/`apps.procurement` have zero awareness accounting exists, same one-directional-dependency principle as everywhere else in this codebase
- [x] Payment Engine — `apps.accounting.Payment`, unified for both directions (received from a customer against an Invoice, paid to a supplier against a Bill); append-only like JournalEntry
- [x] Financial Reports (`apps/accounting/reports.py`) — Trial Balance, Profit & Loss, Balance Sheet, all computed live from `journal_lines` aggregates, no summary tables to keep in sync. Balance Sheet is honest about its one real simplification: there's no period-close mechanism yet, so the current period's net income shows as its own "retained earnings (this period)" line rather than being folded into a real Retained Earnings equity account — the report says so explicitly in a `note` field rather than silently fudging the number
- [x] Company dashboard (`apps/dashboard/views.py`'s `CompanySummaryView`, one endpoint at `/api/dashboard/summary/`) — revenue, expenses, profit, pending receivable/payable (finance), sales order count + value (sales), item count + stock units + low-stock alerts (inventory), active employee count (hr). No dashboard-owned copies of any other app's logic: reuses `apps.accounting.reports._account_totals` for the finance numbers and queries each other app's models directly. Each section is included only if the requesting user has *that section's own* module permission — not one permission gating the whole endpoint — so a single-role user gets a smaller dashboard, not a 403; verified live that an HR Manager sees only the Employees stat while the Owner sees all eleven. Rendered as stat cards on the main `/dashboard` page, above the module tiles.

Frontend: `dashboard/accounting` (Chart of Accounts, Journal Entries with a manual-entry form, Payments, all three reports) and Bills added to `dashboard/procurement` (next to Purchase Orders, matching Invoice's placement next to Sales Orders — both gated by their existing module's permission, not a new one).

Verified end-to-end, backend via curl and frontend via a real browser: an invoice's auto-posted entry (Dr AR 10500 = Cr Revenue 10000 + Cr Tax Payable 500), a payment against it clearing AR to zero and flipping the invoice to paid, the identical loop on the AP side (Bill → Payment paid), an unbalanced manual entry rejected with a clear message, append-only enforcement (405 on PATCH/DELETE) for both JournalEntry and Payment, permission gating (Sales Manager 403, Finance Manager 200) and RLS (a brand-new company gets its own isolated seeded COA and sees zero of another company's journal entries) — and the Balance Sheet identity holding exactly against hand-checked math after a mix of invoice, bill, payment, and manual entries: Assets (450200) = Liabilities (500) + Equity (500000) + Net Income (-50300).

One real bug caught along the way, not in the accounting logic but in a test script: Playwright's `section:has-text("Payments")` does case-insensitive substring matching, and the Journal Entries section's own description text happens to contain the word "payments" — so a locator scoped that way silently grabbed a dropdown from the wrong section. Fixed by scoping via an exact-match heading instead. Worth remembering for any future test that reuses this pattern.

## Phase 3.5 — Platform Hardening (before Industry Modules)

The strategic plan is Core-first, then build Industry-Specific ERPs (Hotel, Real Estate, Retail, Healthcare, Construction) *on top of* this core. That reframes what "done" means here: Phase 4 verticals will reuse Items, Customers, Inventory, Sales, and Accounting rather than duplicating them, so any gap in the core becomes a gap repeated in every vertical built later. This phase is that gap list, grouped the same way it was scoped in conversation.

### Cross-cutting services
- [x] Document Management (attach a file to any record in any module) — `apps.documents`; generic content-type-based attachment with a whitelisted target registry and permission derived from the target record's own module, not a fixed one. Files are served only through a permission-checked `download` action, never a public `/media/` URL. Verified end-to-end: upload/list/download/delete on HR Employee, Sales Invoice, and Procurement Purchase Order; rejected an unlisted-model attach attempt and a nonexistent/cross-company `object_id` cleanly (400, not a crash); confirmed `/media/` itself returns 404 with no route.
- [x] Notification System (in-app first; email later) — `apps.notifications`; `notify_permission()` helper reaches every user holding a given `module.action` permission without callers needing to know which roles carry it. Wired to two real events (low-stock crossing, new Bill) rather than built speculatively ahead of a trigger. Verified end-to-end: both triggers fire with correct message/link, bell badge + dropdown work, mark-one and mark-all-read both work, a user without the relevant permission gets zero notifications, and cross-recipient isolation holds (RLS is the company-membership backstop, the viewset itself narrows to `recipient=request.user`).
- [x] Workflow / Approval Engine — `apps.approvals.ApprovalRequest`, single-step (not a configurable multi-stage chain — the only real consumer needs exactly one decision, so a full chain-of-approvers engine would be speculative). Own whitelist (`apps.approvals.registry.APPROVABLE_TARGETS`) rather than reusing Documents/Notes/Activity/Search's `ALLOWED_TARGETS`, since not everything attachable makes sense to route through approval. Only `procurement.PurchaseOrder` is wired up for real — its `status` already had an unused `APPROVED` value sitting there, the same shape `Item.tax_rate` was in before `apps.tax`. A consuming app registers three hooks (`check_requestable`/`on_requested`/`on_decided`) from its own `AppConfig.ready()`, so `apps.approvals` never imports a specific domain app — same "caller reaches in" shape as `apps.activity`'s signal registration and `notify_permission()`. Segregation of duties enforced server-side: whoever requested approval can't also decide it (403), not just hidden in the UI. `PurchaseOrderSerializer.validate_status()` blocks a client setting submitted/approved/rejected directly, but explicitly allows resending the *unchanged* current value — caught mid-build that the order form always resends `status` alongside an unrelated edit (fixing a line item on an already-approved order), so blocking on mere presence rather than an actual change would have broken ordinary edits to already-decided orders. New `ApprovalPanel` component on the Procurement page's PO rows, matching the Documents/Notes/Activity panel shape. Verified end-to-end via Playwright: a real UI request flips PO status draft→submitted; a direct client PATCH to `approved` is rejected (400); the requester is blocked from approving their own request (403); a second user holding the same `procurement.manage` permission approves successfully; editing lines on the approved PO while resending the unchanged status still succeeds; re-deciding an already-decided request is rejected (400); a duplicate pending request on the same record is rejected (400); reject (with a decision note) flips status to `rejected` and notifies the requester; and re-requesting is correctly blocked until the record moves back to Draft.
- [x] Tasks (not originally on this list, but built as part of working through `docs/MODULE_MAP.md`'s Core Platform section in order) — `apps.tasks`, a standalone company-wide task list (title, assignee, due date, status). New `GET /api/companies/members/` endpoint backs the assignee picker. Every default role gets `tasks.manage` — shared productivity infrastructure, not gated like most modules. Verified end-to-end: create/edit/delete/inline-status-change all round-trip through a real server refetch, not just optimistic UI state.
- [x] Calendar (same reason as Tasks — next item in `docs/MODULE_MAP.md`'s Core Platform section) — `apps.calendar.Event` for standalone entries, plus a `/dashboard/calendar` month grid that aggregates existing Task/Invoice/Bill due dates live rather than duplicating them. Introduced `SHARED_PERMISSIONS` in `apps/roles/seed.py` (dashboard/settings/tasks/calendar view+manage) since hand-duplicating the same lines onto all five `DEFAULT_ROLES` entries a fourth time was a clear enough pattern to refactor. Caught a real timezone bug during testing — an all-day date routed through `Date`/`toISOString()` crosses UTC and can shift the calendar day for non-UTC users — fixed by keeping dates as plain strings throughout; verified the fix by confirming a `2026-08-23T00:00:00Z` event landed exactly on day 23, not 22 or 24.
- [x] Notes & Comments (next item in `docs/MODULE_MAP.md`'s Core Platform section) — `apps.notes.Note`, the same generic `content_type`/`object_id` attachment pattern as Documents, sharing the exact same target whitelist. That second real consumer is what justified extracting `apps/documents/registry.py` into `apps/common/targeting.py` (`ALLOWED_TARGETS` + `resolve_target()`) instead of duplicating it — the project's established rule of not abstracting until a pattern is proven needed twice. Wired into HR Employee, Sales Invoice, and Procurement Purchase Order via a `NotesPanel` component mirroring `DocumentsPanel`. Found and fixed a real bug while testing: `DocumentViewSet.list()` and the new `NoteViewSet.list()` both tried to narrow results by assigning `self.queryset = ...` before calling `super().list()`, but both viewsets override `get_queryset()` to ignore `self.queryset` entirely — so every `list()` call was silently returning *every* document/note in the company, not just the ones for the requested record (caught via a Playwright test showing a brand-new employee's "Files" count as 4 instead of 1). Fixed both viewsets by having `get_queryset()` read back an explicit `_list_content_type`/`_list_object_id` pair that `list()` sets first. Verified end-to-end via Playwright (create/edit/delete round-trip through real server refetches) and direct API checks: unlisted-model rejected on both list (404) and create (400), a nonexistent/cross-company `object_id` rejected on create (400), and a valid create against a real record succeeds (201).
- [x] Activity Timeline (next item in `docs/MODULE_MAP.md`'s Core Platform section) — `apps.activity.Activity`, a third consumer of the same `ALLOWED_TARGETS` whitelist Documents and Notes already share. Deliberately read-only through the API: entries come from a `post_save` signal connected once per whitelisted model in `ActivityConfig.ready()` (auto-logs "created"), plus two explicit `log_activity()` call sites added to `NoteViewSet.perform_create`/`DocumentViewSet.perform_create` ("note added"/"document attached") rather than a blanket signal for every kind of event, since those are the only two events that exist yet. The signal has no `request` to read an actor from, so it reads a small thread-local (`apps.common.current_user.get_current_user()`) that `CurrentCompanyMiddleware` now sets/clears around every request — the narrowest fix that solves this one problem, not a general request-context system. Applied the same `get_queryset()`-reads-back-`_list_content_type`/`_list_object_id` fix from the Notes bug preemptively, since `ActivityViewSet` is built on the identical `list()`-narrows-a-generic-queryset shape. Wired into the same three proof points via an `ActivityPanel` component. Verified end-to-end via Playwright: creating an employee, adding a note, and attaching a file produced exactly the three expected timeline entries scoped to that one record; unlisted-model list rejected (404), missing query params rejected (404), and create correctly unreachable (read-only viewset, router never binds POST).
- [x] Global Search (next item in `docs/MODULE_MAP.md`'s Core Platform section) — `apps.search.GlobalSearchView`, one endpoint rather than each module owning its own search box; the fourth consumer of `ALLOWED_TARGETS`, adding only `search_fields`/title format on top in `apps.common.search_targets.SEARCH_TARGETS`. Skips `PurchaseOrder`/`Quotation`/`SalesOrder` on purpose — none has an own text field, just `<Prefix>-<id>` over a related Customer/Supplier — those stay findable through that related record instead of forcing a join-based search this early. A model is excluded from a user's results per-model, before it's ever queried, if they lack `view` on its permission_module — same enforcement point the rest of the app uses, not a post-hoc filter. Frontend is a debounced `GlobalSearch` box in `AppHeader` (≥2 chars, 250ms), capped at 30 results total / 5 per model. Verified end-to-end via Playwright: a newly created employee is findable by name from an unrelated page in one search; a 1-character query shows no dropdown; and, the check that actually exercises the permission gate rather than just the UI, a second demo user with only `accounting.view`/`manage` (no `hr.view`) gets zero results for the same term that the owner found instantly.
- [x] Audit Logs (next item in `docs/MODULE_MAP.md`'s Core Platform section, and the first one flagged with a "MiranErp has a portable version" caveat) — `apps.auditlog.AuditLog`. Per the standing "don't copy MiranErp code, let's talk first" instruction: read MiranErp's `apps.auditlog` for reference (its model, its `CompanyScopedMixin`-level hook, its serializer-diff approach), discussed it with the user, then wrote CoreERP's own version from scratch — no MiranErp code copied in. That comparison changed the design for the better in three concrete ways versus what would otherwise have been built blind (a per-model signal-based approach, mirroring `apps.activity`): (1) writes happen from exactly one place, `CompanyScopedMixin.perform_create`/`perform_update`/`perform_destroy` in `apps/common/views.py` — the shared base every `CompanyScopedViewSet`/`CompanyScopedReadOnlyViewSet` already builds on — so all ~20 existing viewsets got audit coverage from one change, no per-app wiring, no thread-local actor hack needed (unlike Activity's, since `self.request` is right there in the mixin); (2) diffs are computed by serializing the instance through the viewset's own serializer before and after `save()`, not raw model-field comparison, so a diff shows exactly what the API itself would show; (3) coverage is intentionally broader than `apps.activity`'s `ALLOWED_TARGETS` whitelist — master data like `Warehouse`/`Account` gets audit-logged too, confirmed directly, since attachability and auditability are different concerns. Caught one real bug purely from reading MiranErp's `perform_destroy` before writing CoreERP's own: Django resets `instance.pk` to `None` once `.delete()` completes, so the audit write has to happen *before* `instance.delete()`, not after, or the deleted entry's `object_id` would be `None` — this is exactly the kind of bug "compare first" is for, catching it during design instead of via a failing test. Read access is a single strict gate, `settings.manage` (Owner-level) even for one record's own history — deliberately stricter than Activity's `<module>.view`, since a cross-module change trail is more sensitive data than any one module's own records. New `/dashboard/audit-log` page, linked from Settings, admin-only. Verified end-to-end via Playwright: create→update→delete on an Employee produced all three entries with an accurate field diff on the update (`last_name`, `position` both captured correctly) and a correct `target_label` on the delete entry (confirming the pk-reset ordering was handled right); a non-admin role gets 403 on both the company-wide and per-record endpoints; and a regression check confirmed ordinary CRUD still works normally on two unrelated apps (Customer, Warehouse) after the shared-mixin change, with Warehouse's own audit entries confirmed directly in the database to prove the broader-than-`ALLOWED_TARGETS` coverage claim.
- [x] Tax Configuration (the second and last item flagged with a MiranErp caveat) — `apps.tax.TaxRate`, built the same way as Audit Logs: read MiranErp's `apps.tax` for reference, then wrote CoreERP's own version, not a port. `Item.tax_rate` changes from a decorative flat decimal (nothing ever computed from it) to a real FK — tax is opt-in per item, driven by whichever company-configured `TaxRate` each item carries, not one global percentage. Two deliberate departures from MiranErp's version rather than a copy: dropped the hotel-specific `applies_to_room_charges` flag and its tax-inclusive-total engine variant (Core's line items are always net-of-tax, so there's no industry-specific inclusive-total case to carry over); and seeded zero default rates, since MiranErp hardcodes its actual Ethiopia VAT/Tourism-levy numbers — correct for one real deployment, wrong to assume for a platform with no fixed jurisdiction. `apps.tax.engine.compute_line_tax_cents(lines)` plugs into `InvoiceSerializer.create()`/`BillSerializer.create()` right alongside where `amount_cents` already gets snapshotted from a linked SalesOrder/PurchaseOrder's total — a standalone Invoice/Bill (no order) is untouched, keeping its existing manually-entered tax amount since there are no lines to compute from. New Settings section for managing rates (`settings.manage` to edit, `settings.view` to see them — same split as Branches), and the Item form's tax input changed from a free-text percentage to a dropdown of active rates. Verified end-to-end via Playwright: a real UI flow (add a 15% VAT rate in Settings, assign it to a new Item in Inventory) followed by API-driven PO→Bill and SalesOrder→Invoice flows confirming `tax_amount_cents` computed exactly right (1500 cents on a 10000-cent net total, both directions); and a second item with no rate assigned correctly produces zero tax on its invoice, confirming the "opt in per item" behavior holds.
- [x] Expenses (`docs/MODULE_MAP.md` Section A's remaining items — Localization/Multi-language/Multi-currency — had no concrete gap to close, unlike everything above; moved to Section B instead, starting with Expenses, explicitly flagged there as "a real gap") — `apps.expenses.Expense`. New `EmployeePickerView` in `apps.hr` (mirroring `CompanyMembersView`'s existing precedent) lets any member populate the employee dropdown without needing `hr.view`. Registered in all four existing whitelists (`ALLOWED_TARGETS`, `SEARCH_TARGETS`, `APPROVABLE_TARGETS`) as one-line additions each — confirming those registries generalize to a genuinely new module, not just the ones they were designed around. Verified end-to-end via Playwright — the most complete single-feature test this session: filed via the real UI → receipt attached via Documents → approval requested → confirmed no journal entry exists yet → requester blocked from self-approving (403) → a second user with the same `expenses.manage` approves → journal entry posts with the correct Dr/Cr amounts → a real Payment recorded through the Accounting page's UI flips it to Paid → found via Global Search → the full lifecycle visible in the Audit Log.
- [x] Cash Flow (Section B, second item) — `apps.accounting.reports.CashFlowView`. Chosen deliberately over the also-real Financial Periods/Period Closing gap: closing the books properly would also require date-range filtering on the existing all-time-only reports (explicitly out of scope per `reports.py`'s own docstring), making it a bigger, riskier two-part change on a ledger feature — Cash Flow is purely additive instead, the same live-computed pattern as Trial Balance/P&L/Balance Sheet, no new models, no risk to existing data. Direct method, sourced from the Cash-role account's own `JournalLine`s as the total (not just `Payment` records), so a manual Journal Entry touching cash is never silently missed — the Payment-derived categories (received from customers/paid to suppliers/paid to employees) are a human-readable breakdown of that same total, with any gap surfaced honestly as `other_cash_movements_cents` rather than dropped. Deliberately Operating-only, not the conventional three-section statement, since CoreERP doesn't yet generate any Investing/Financing cash movement — two permanently-empty sections would be more misleading than one section that's always accurate. Verified end-to-end via Playwright: a real customer payment (12345 cents) and supplier payment (6789 cents) moved the report's category totals and net change by exactly the right amounts; the Accounting page's UI renders the updated figures and scope note; a non-accounting role gets 403, matching the other three reports. Incidentally caught a real piece of leftover test data (an orphaned Payment journal entry with no matching Payment row) via `other_cash_movements_cents` correctly flagging it — a live demonstration of why reconciling against the ledger's own JournalLines, not just Payment records, was the right call.
- [x] Receipts (Section B, third item — closing the `docs/MODULE_MAP.md`-flagged *(partial)* gap: "a Payment record exists; no separate printable Receipt document") — `Payment.receipt_number`, generated via `apps.common.numbering.next_number()`, a third real consumer of that engine after Invoice/Bill (exactly the case it was built to generalize for). ### Platform primitives (surfaced reviewing what Hotel/Real Estate/Retail/Healthcare/Construction will actually need — see chat)
Two of these are structural enough that retrofitting them after several vertical modules exist would be much more painful than adding them now, so they jump the queue ahead of the cross-cutting/team-growth items above:
- [x] **Branch/Location Management** — almost every real company in the target verticals (a hotel with multiple properties, a retail chain, a real-estate office network) operates across more than one physical location. `apps/branches.Branch` (company-scoped, same RLS pattern as everything else), with an optional `branch` FK added to Department, Employee, and Warehouse — the three models where "which location" is obviously meaningful today. Gated by a new `settings.view`/`settings.manage` split (previously only `settings.manage` existed, which would've locked everyone but the Owner out of even seeing the branch list needed to assign records to one) — `settings.view` was added to every default role's seeded permissions, with a data migration re-seeding existing companies so the change applies retroactively, not just to newly-created ones. Frontend: new `/dashboard/settings` page (Company profile edit + Branch management), and the previously-inert "Settings" dashboard tile now links to it. Extending `branch` to other modules (Customers, Sales/Procurement documents, etc.) is deliberately left for whenever a real need shows up rather than done exhaustively now.
  - Caught a real bug while building this: the data migration's `Company.objects.all()` returned zero rows and silently did nothing, because migrations run outside a request — `CurrentCompanyMiddleware` never fires, so the RLS session vars are unset and `companies`' `FORCE ROW LEVEL SECURITY` policy hides every row. Same root cause as the documented company-bootstrap RLS gotcha; fixed with the same `SET LOCAL app.is_platform_admin = 'true'` bypass, scoped to the migration's own transaction.
  - Verified in a real browser: Owner adds a branch, edits its address, assigns an Employee and a Warehouse to it (both show the branch name back correctly); a non-Owner role (HR Manager) can see the branch list but gets no Add/Edit/Delete controls and disabled company-profile fields — permission split confirmed both ways.
- [x] **Numbering Engine** — `apps/common.NumberSequence` + `next_number(company, code)`, a shared per-company/per-document-type atomic counter (`select_for_update` inside a transaction), replacing the ad hoc `f"INV-{company_id}-{id:05d}"` string-building that Invoice and Bill each had independently. Ready for Purchase Orders, Sales Orders, Quotations, or Employee numbers whenever those modules want a real number instead of `PO-{id}`/`SO-{id}` — not retrofitted onto them speculatively here. Verified via curl: three invoices in a row issued `INV-00001`, `INV-00002`, `INV-00003`; a bill issued `BILL-00001` independently. Known cosmetic quirk, not a bug: this dev database already had a few invoices numbered under the old `INV-{company_id}-{id}` format from earlier sessions — those keep their old-format numbers (no backfill/renumbering was done, and the two formats can't collide under the `unique(company, invoice_number)` constraint since they're different shapes), so a from-day-one company won't see this at all.
- Deliberately **deferred until a real trigger**, not built speculatively: Currency Engine (wait for an actual multi-currency company — FX revaluation is expensive to get right without a real case to validate against), Tax Engine beyond the current flat `tax_rate` field (wait for the first vertical that needs more than one flat rate, e.g. Hotel's Tourism Tax), Activity Timeline, Comments, Tagging (all cheap to bolt on later, don't shape the schema), Background Jobs / async (Celery+Redis stood up with nothing queued yet is premature — trigger off the first real async need, e.g. sending an invite email), PDF Engine, Import/Export.
- Deliberately **out of scope**, reconsider only if a specific vertical demands it: global Search, Dashboard Builder, Calendar/Tasks/Chat/Announcements — these are products in their own right (Slack/Asana territory) and would dilute focus from "foundation for industry verticals." API versioning (`/api/v1/`) costs nothing to add later by prefixing routes, so there's no reason to do it ahead of need. Mobile API is already satisfied — it's plain REST/JSON already, nothing vertical-specific to build.

## Open risks to revisit (from architecture doc §11)

- [x] RLS policies written and tested for the Phase 1 tables — pattern established (`current_user_company_ids()` SECURITY DEFINER function) for Phase 2 tables to reuse rather than reinvent. Learned two sharp edges worth remembering: (1) a policy can't safely reference its own table in a subquery — Postgres detects it as infinite recursion; (2) `INSERT ... RETURNING` (which Django's ORM always uses) is subject to the `USING`/SELECT policy too, not just `WITH CHECK` — so a row that grants its own visibility (like a company's first membership) needs a scoped `SET LOCAL` bypass at creation time.
- [x] Multi-company "active company" UX validated with a real multi-membership user — gave a user memberships in two companies and confirmed the `same_company_fields` check (not RLS, which is member-of-any-company-scoped by design) is what actually catches "wrong company active" mistakes on FK fields
